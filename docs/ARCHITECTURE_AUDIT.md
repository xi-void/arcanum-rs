# Architecture audit

## Executive assessment

Arcanum-RS passes the standalone core acceptance criterion. A clean checkout of the tracked files built offline and passed all 69 portable tests in a Linux sandbox without access to CE, TIG, original game assets, or external mods. The current CLI and library own resource access. CE is a source of evidence and an optional development oracle. A playable standalone engine still needs substantial Rust implementations above the resource and content layers.

The audit found no Critical findings or current High-severity defects. Three Medium findings matter before runtime integration. Schematic reference completeness can coexist with an unusable item or unreadable illustration, item-name validation differs across loaders, and Armour's native projection omits signed complexity needed to interpret magical adjustments. Synthetic probes also exposed two lower-severity diagnostic limitations. The current installation still produced 119 structurally supported and reference-complete learned and found recipes under the existing audit contract.

Native identities can already name a new item, effect, or recipe without a legacy ID. The only shipped content loaders require legacy resources. A mod can supply arbitrary files and declare package dependencies today, while it cannot yet register or cross-reference native definitions from those files. A third ingredient is a concrete restriction of the native recipe type.

## Findings

Severity describes current behavior and model limitations. Future implementation gates are listed separately.

### M1 · Medium · Reference-complete recipes can point to unusable content

[Prototype load modes](../src/content/items.rs#L523) · [Schematic item resolution](../src/content/schematics.rs#L543) · [Illustration lookup](../src/content/schematics.rs#L463) · [Summary](../src/main.rs#L527)

- **Evidence and reproduction.** The synthetic 4200 fixture below reported `1 complete / 1 audited` with a 143-byte Weapon ending after its description. Detailed inspection failed at byte 143 with “truncated field”. In a separate run with the full Weapon body, an illustration supplied by a DAT entry with a valid index but a malformed compressed payload also passed the audit. Extraction rejected the payload. There is no ART-format decoder involved in the latter experiment.
- **Impact.** The current audit establishes recipe construction, identity and name resolution, and an illustration path winner. Food receives more body validation than other recipe item references. A mod can pass this audit and fail later when the game loads the referenced item or drawing. The 119 stock count remains valid under its existing scope.
- **Smallest correction and timing.** Label the current check as reference resolution. When a runtime consumer needs validated content, explicitly verify the supported item definitions and asset readability it requires. This distinction is required before treating the audit as a runtime loading gate. Generic and Key bodies can stay out of scope until a consumer requires them.

### M2 · Medium · The native Armour projection drops a verified scaling input

[Armour fields](../src/content/items.rs#L126) · [Projection](../src/content/items.rs#L367) · [Legacy fields](../src/prototype.rs#L344). CE `src/game/item.c:482`, `item_armor_ac_adj`, and `src/game/object.c:1680`.

- **Evidence and reproduction.** Two synthetic versions of the same Armour, with signed complexity `+30` and `−30`, produced the same native projection, including a negative Physical adjustment and explicit zero Magic adjustment. The raw report distinguished the versions. The installed Ring of Protection (+40) and Machined Platemail (−30) establish that both signs are used by real content. CE calls the direct scaling branch for positive complexity and the complementary branch for negative complexity.
- **Impact.** AC and resistance systems driven by the current native definition alone cannot recover which rule applies. Reaching back into raw prototype data would make those systems depend on the legacy import path and leave native mod items without an equivalent.
- **Smallest correction and timing.** Carry the verified aptitude interaction as native item data before implementing direct equipment contributions. Keep raw complexity and format details in the importer and character aptitude and identification in runtime state. The current inspector can remain useful as a partial view.

### M3 · Medium · A whitespace-only item name passes one resolver and fails the other

[Schematic text lookup](../src/content/schematics.rs#L413) · [Standalone item name lookup](../src/content/items.rs#L455)

- **Evidence and reproduction.** With a fully framed Weapon and MES record `{400}{   }`, synthetic 4200 still reported complete. `prototype inspect` rejected that same stored key. MES legitimately supports whitespace values, so the policy belongs to the item-name consumer.
- **Impact.** A whole-table override can produce an item identity and blank name in a recipe while failing the definition loader. The two consumers disagree about usable content.
- **Smallest correction and timing.** Share the item-name check for those paths and exercise it with a regression fixture. Apply the policy to item display names. This belongs before using audit results to validate gameplay content.

### L1 · Low · Effect inspection drops duplicate-key evidence

[Effect load and report](../src/content/effects.rs#L218) · [MES inspection](../src/main.rs#L283) · [Effect inspection](../src/main.rs#L300)

- **Evidence and reproduction.** A synthetic mod supplying `{128}{ac -1}{128}{ac -2}` produced a correctly attributed mod winner and `−2` in effect inspection. The effect report had no duplicate information. MES inspection of the same winner reported one duplicate. An omitted base row, 54, was missing with the mod enabled and available without it, consistent with full-table replacement.
- **Impact.** A mod author can mistake an accidental duplicated effect for a clean import. The winning value and provenance are deterministic.
- **Smallest correction and timing.** Retain and show duplicate information for the selected effect key, as the schematic resolver does. This can follow the runtime gates.

### L2 · Low · Detailed inspection validates interpreted arrays more deeply than opaque arrays

[Interpreted sparse arrays](../src/prototype.rs#L539) · [Opaque array framing](../src/prototype.rs#L601)

- **Evidence and reproduction.** A two-value resistance array whose mask was changed to one set bit failed. The same prototype still passed detailed inspection with a well-framed common overlay declaring one value and a zero-bit mask. Count and mask disagreement in an opaque field is currently invisible to the caller.
- **Impact.** A detailed report can be misread as a full binary validity check. Decoded fields in the probe remained valid.
- **Smallest correction and timing.** Keep diagnostics scoped to validated fields. Require the cardinality invariant for an opaque slot when that slot is promoted to an interpreted field or included in a stronger validity contract. No blanket parser expansion is needed before runtime.

## Standalone engine independence

| Dependency class | Audit result |
| --- | --- |
| Reference only | CE source informed stock mount precedence and sidecars, legacy field framing, sparse ranking, basic-ID conversion, descriptions and art lookups, schematic variants, and effect interpretation. The current compatibility policy and import conversions use Rust code. CE's runtime formulas and script algorithms were consulted as behavioral evidence. |
| Development-time verification | Historical TIG and MES probes were external and optional. The tracked installed tests opt in to game resources and the smoke mod, with no link or execution dependency on CE. The standalone sandbox exercised all portable tests with those inputs hidden. |
| Temporary adapter | The architecture allows a future CE consumer through a narrow interface. No tracked CE ABI adapter, FFI entry point, build/link script, CE crate, or subprocess invocation exists in the core. A future adapter must own any handle conversion and host lifecycle on its side of the boundary. |
| Runtime | No hidden CE or TIG library, executable, memory layout, initialization, or working-directory dependency was found. The Linux CLI linked only the platform loader, libc and libgcc_s. Original game content remains an input for playing the original campaign. Asset compatibility is independent of engine linkage. |

Dependency direction is consistent with [the architecture](ARCHITECTURE.md). Callers own VFS state and pass it into importers. The stock discovery profile and CE lookup policy belong to resource compatibility. An empty ordered VFS can be constructed and mounted without discovering a game. Legacy reader types are public for inspection, while the native item, recipe and effect structs can be constructed independently. Keep future runtime APIs downstream of validated definitions. Do not feed them legacy field numbers, object IDs, script counters, art bit layouts or CE slot positions.

| Subsystem | Standalone work remaining or evidenced boundary |
| --- | --- |
| Resource management | DAT, bounded reads, VFS, mount planning, and text import already have Rust implementations. Future asset decoders, streaming and campaign resource lifecycle need their own Rust ownership. There is no TIG resource manager to remove. |
| Game rules and combat | Equipment, inventory, character progression, stats, aptitude, timing, targeting, attacks and damage need independent runtime code. CE is evidence for particular formulas. Signed Armour adjustments, attack-specific ammo use and channel-specific calculations need independent inputs and test vectors. |
| Scripting | The current report resolves numbered script files. It does not execute them or express their conditions as native data. A legacy script translator or interpreter and a native scripting interface would need explicit actor/source identities and an engine-owned contract for events, effects and persistent state. |
| World simulation | Maps, entity ownership, time, movement, AI, quests and transitions need standalone semantics. Original object or instance layouts can inform an importer. They should stay outside the world model. |
| Rendering, audio and input | No implementation for the standalone game exists in the audited core. Internal resource identifiers should resolve to data consumed by Rust-owned rendering, audio and input systems without TIG initialization. |
| Save/load and persistence | No runtime state format is frozen. Native persistent identities and versioned state need to represent actors, items, scripts and live grants. Any future legacy save reader must translate at the boundary. CE pointers, global arrays and object order cannot be the native identity contract. |

For any functionality derived from CE, require independent Rust ownership and native interfaces, a review of licensing and provenance before adopting algorithms, and tests that can run without the reference engine. Prefer data checks, independently derived vectors and optional differential tests that expose disagreements with CE. Keep adapter tests separate from portable tests.

## Native modding independence

**Can a future mod define an item, effect or technological schematic without a prototype, numeric ID or CE?** Yes for the native identities and the verified shapes already expressible in Rust. A data-only mod has no such registration path today. A temporary consumer constructed a Food definition with `smithing:item/tonic`, an effect with `smithing:effect/ward`, and a recipe with `smithing:recipe/tonic`. Its input references included the original `arcanum:item/prototype-10087` and a potential external `metals:item/catalyst`. Construction required no legacy loader. The external ID in this probe was a reference value. No package resolver checked that it existed.

## Effect semantics and runtime readiness

- **Equipment state.** Nominal coverage and fit are useful definition fields. Ring placement, hands, race and gender restrictions, and the Generic Lantern's shield flag require rules and state beyond that view. State ownership and stable item-instance identity should precede equip events. These requirements do not depend on the final armour calculation.
- **Character stats and aptitude.** Treat base properties, direct adjustments, other active effects and query-specific caps as distinct stages. Ring of Protection's +10 AC and Physical adjustment are stored numbers subject to runtime conditions. Machined Platemail gives negative adjustments in the same field family. Before implementing either scaling path, retain complexity semantics and verify sign, rounding, identification gates and query differences. The CE resistance path adds Constitution only for Poison, and its final 0–95 clamp has a monstrous-NPC exception. Other query paths, particularly magic resistance and fatigue mitigation, need their own evidence.
- **Effect evaluation.** CE collects by target and operation kind, then applies percent, multiply, divide, sum, minimum and maximum in that order. A tighter upper bound can reduce the result below an intermediate floor. Body of Fire's 97% Poison floor remains 97 in the definition and can yield 95 in an ordinary queried result. Text order has no execution meaning in the reviewed CE path. The runtime needs explicit evaluation phases, conflict rules and integer bounds before it consumes these definitions. The selected definitions contain no maximum. Wider same-target interactions remain CE source evidence and need independent cases before reuse.
- **Activation and removal.** Sword of Defense effect 128 adds one AC point per activation copy. The attachment calculates a count up to 15, with zero at aptitude −94 and one at −93 in the reviewed path. It saves the count and removes using that saved value. CE also uses an off/on refresh during aptitude changes. A native grant needs the original granted amount or equivalent operation instances, a distinct grant identity, a source item instance, target, and lifetime. With activations from A then B, removing B through CE's first-match-by-definition function removes A's first match. This is a source-level counterexample to using definition IDs for ownership, without a gameplay claim about the visible total. Native off, expiry and refresh should operate on the correct grant, including after aptitude changes.
- **Script execution.** Distinguish script resource, attachment or event, invocation context, and the grant it produces. Script numbers and original attachment counters may be decoded by an importer, while the standalone runtime owns the events and persistent state. Rust effect inspection of a synthetic 401 succeeded even though CE registers engine-wide IDs 50–399 from `effect.mes` and module IDs 0–49 from `gameeffect.mes`. Inspectability cannot establish registration or execution. No registry decision is needed for standalone readers.
- **Combat.** Weapon damage channel order differs from the resistance channel order. Speed is a rating, range uses tiles, and the Bullet prototype's raw quantity 10 is distinct from the Flintlock's base consumption of one and a future instance's current quantity. CE has attack-specific overrides. Effective attack rules, spawn quantity policy and channel-specific mitigation can wait until the relevant systems have testable inputs. The Fortifier CE inventory issue is still open.

CE reference locations include `src/game/effect.c:257,313,542,742`, `src/game/object.c:1680`, `src/game/item.c:482,2974,3000,3220`, `src/game/stat.c:773`, and `src/game/script.c` around the effect actions and `SAT_GET_MAGICTECH_ADJUSTMENT`. The script byte and condition evidence for Sword of Defense is recorded in [the content findings](CONTENT_FORMATS.md#sword-of-defense-wield-scripts).

## Recommended corrections in priority order

1. Separate reference coverage from runtime-ready definitions and share the item-name validation rule (M1/M3). Preserve existing raw provenance in either result.
2. Carry the verified scaling input into the native Armour boundary before direct contribution calculations (M2). Define activation ownership and the stored-versus-effective distinction before connecting any script or equipment event to effect evaluation.
3. Before releasing a native authoring format, validate namespace ownership and cross-package references. Preserve the two-input legacy importer and demonstrate a data-only item, effect and schematic with declared dependencies before freezing native schema constraints.
4. Surface selected effect duplicates and describe opaque array validation accurately (L1/L2). Leave archived encoding exceptions explicit until a justified encoding selection or translation is available.

The core is ready for standalone development and a small definition-loading follow-up. A connected equipment, stat, effect or combat runtime should wait for the relevant inputs and ownership boundaries above. **Milestone 16** should tighten the content validation contract around schematic references and directly usable definitions, including one synthetic override that currently passes reference resolution and fails item loading. This can preserve all 119 recipes and stay independent of CE.
